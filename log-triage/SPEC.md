# SPEC · 日志体检器（log-triage）

> 状态：**待实现**（规格已定，可直接开工）
> 优先级：🥇 高（系统运维 / 应用实施 / IT 支持岗都对口）
> 预估：1~2 天｜归属：`projects/log-triage/`

---

## 1. 一句话

把一个目录下所有日志喂进去，出一份"到底有几种错、什么时候开始、最早出现在哪"的报告。

## 2. 输入 / 输出

| | 说明 |
|---|---|
| 输入 | 日志目录（命令行参数，不写死）；支持 `.log` / `.txt` / `.json` 行式 |
| 输出 | `triage-report.md`；可选 `summary.json` |
| 规模要求 | 至少能吃下 **100MB / 几十万行**而不明显卡（流式读，不整份载入） |

## 3. 报告必须包含

1. 总行数 / 文件数 / 时间跨度（最早 → 最晚）
2. 级别分布：INFO / WARN / ERROR / FATAL（**格式认不出来时要标"未知级别"，不许瞎猜**）
3. **错误类型 Top N（必须归并）** ← 这是核心价值
4. 每类错误：**首次出现时间、末次出现时间、出现次数、首次出现的文件:行号**
5. 时间分布（按小时/天），标出**错误开始密集出现的时间点**
6. 可疑线索：例如"某类错误在某个时间点后突增"

## 4. 归并规则（与 `model-call-report` 保持一致，可复用同一套函数）

完整 UUID → `<uuid>`；长十六进制 → `<id>`；IP → `<ip>`；路径 → `<path>`；数字 → `N`。

## 5. 验收标准

- [ ] 用**真实日志**跑（网关日志、本机服务日志、系统事件日志都行）
- [ ] **单元测试 ≥10 项**：归并、级别识别、时间跨度、首次/末次定位、空目录、超大文件分块读取
- [ ] 零第三方依赖
- [ ] **有一个"归并前后对比"**：报告里能看出原始 N 行被归并成 M 类
- [ ] README 含"什么日志都能吃 / 什么格式认不出来"的诚实边界

## 6. 明确不做

- 不做实时监控、不做告警推送（这是**事后体检**）
- 不解析具体业务语义（不知道你的业务，只做通用统计）
- 不做图表

## 7. 面试可讲的点

> "排障最花时间的不是看日志，是**从几千行里找出到底有几种错**。
> 我写了个工具做这件事，关键是**同类错误要归并**——
> `timeout after 123ms` 和 `timeout after 456ms` 算同一类，
> 不归并的话 Top N 里全是重复行，报告就是废的。"
