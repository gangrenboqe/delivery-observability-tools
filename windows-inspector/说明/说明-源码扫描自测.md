# 说明 - 源码扫描自测

> 项目：windows-inspector · 读者：完全不懂技术的第一次求职者 · 写作日期：2026-10-11

## ① 一句话是什么

让测试去检查代码本身，守规不过关就判测试失败。

## ② 为什么需要它

像「只用查询命令、不许出现删除文件的命令」这类纪律，靠人记忆和口头约定一定会破——改代码的人多了、时间久了，总会有人顺手加一行坏命令进去。

把纪律写成自动检查：测试直接读取程序自己的源代码文本（源码扫描），发现违禁词就让测试失败。纪律从「靠自觉」变成「机器把关」，谁破坏守则，跑测试立刻红灯。

没有它会怎样：「只读」「安全」沦为文件里的一句口号，没有任何机制兜底。

## ③ 在我们项目里长什么样

- 代码在 [Test-Inspect.ps1](file:///E:/DSHPersonalAI/projects/windows-inspector/Test-Inspect.ps1)（自测脚本，共 58 条断言，全部通过）
- 其中一组断言用 Get-Content -Raw（PowerShell 的一次性读整个文件的命令）把 [Inspect-Windows.ps1](file:///E:/DSHPersonalAI/projects/windows-inspector/Inspect-Windows.ps1) 的源码整个读进来，断言里面不出现修改类命令，共守 8 条禁令，例如：Set-Service（改服务状态）、Stop-Process（强制结束进程）、Remove-Item（删除文件）等
- 不依赖第三方测试框架（不依赖 Pester——Pester 是 PowerShell 社区常用的测试框架）：全部用 Windows 自带的标准语法写，拿到任何一台 Windows 电脑都能直接跑
- **实战战果（都是这类自测先抓到的真 bug）**：
  1. `HigherIsWorse` 方向开关没被读取，三档判断方向颠倒
  2. 参数改名后调用处没同步（集成层漏测的教训由此补上集成测试）

## ④ 面试怎么讲（约 45 秒）

「我把『只读』这条红线做成了测试：自测脚本把主程序源码整个读进来，断言里面不许出现修改服务、强制结束进程、删除文件这类命令，一共守八条禁令。为什么这么做？因为纪律靠自觉一定会破，写成断言之后，谁改坏了守则，跑测试立刻红灯。整套 58 条断言不依赖第三方测试框架，拿到任何一台 Windows 都能直接跑。这个项目里抓到的两个真 bug——判断方向颠倒、参数改名不同步——都是这类自测先发现的，证明这道防线值得建。」

## ⑤ 常见误解 / 坑

- **误解**：「测试只能测程序运行的结果」。源码本身就是可检查的对象，纪律类约束特别适合这么测。
- **我们踩过的坑（实战教训）**：违禁词清单不全，漏一种就破防；清单要随着新认识的命令持续补充。另外「暂时注释掉的坏命令」也算数，不能因为是注释就放行。
- **坑**：测试依赖特殊框架，换台机器就跑不起来。我们选纯标准语法，用一点便利性换通用性。
